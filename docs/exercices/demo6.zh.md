# 第一部分 — 理论

## 1. 映射 ADT（§10.1.1）

**映射**（关联数组）存储称为**条目**（*entries*）的**键–值**对 $(k, v)$。

键是**唯一的**：键 → 值的关联定义了一个*函数*（数学意义上的）。

### 基本操作

| 操作          | 描述                                                         |
|---------------|--------------------------------------------------------------|
| `get(k)`      | 返回与 $k$ 关联的值，若不存在则返回 `null`                   |
| `put(k, v)`   | 插入 $(k,v)$ 或替换已有值；返回旧值或 `null`                 |
| `remove(k)`   | 删除该条目并返回其值，若不存在则返回 `null`                  |
| `size()`      | 条目数量                                                     |
| `isEmpty()`   | 测试映射是否为空                                             |
| `keySet()`    | 可迭代的键集合                                               |
| `values()`    | 可迭代的值集合                                               |
| `entrySet()`  | 可迭代的 $(k,v)$ 对集合                                      |

!!! warning "`null` 的歧义性"

    `get(k) == null` 可能有两种含义：

    - 键 $k$ 在映射中**不存在**，或
    - 键**存在**但与值 `null` 关联。

    在 Java 中，`containsKey(k)` 可用于消除歧义。

### 执行轨迹示例（教材例 10.1）

| 操作          | 返回值  | 映射状态                                |
|---------------|---------|-----------------------------------------|
| `put(5, A)`   | `null`  | {(5,A)}                                 |
| `put(7, B)`   | `null`  | {(5,A), (7,B)}                          |
| `put(2, C)`   | `null`  | {(5,A), (7,B), (2,C)}                   |
| `put(2, E)`   | `C`     | {(5,A), (7,B), (2,E)}                   |
| `get(7)`      | `B`     | 不变                                    |
| `get(4)`      | `null`  | 不变                                    |
| `remove(5)`   | `A`     | {(7,B), (2,E)}                          |

## 2. 简单实现：UnsortedTableMap（§10.1.4）

将条目存储在一个无序的 `ArrayList` 中。

每次操作都需要**线性扫描**来查找键。

| 方法        | 复杂度     |
|------------|------------|
| `get(k)`   | $O(n)$     |
| `put(k,v)` | $O(n)$     |
| `remove(k)`| $O(n)$     |

!!! tip "删除技巧"

    为避免 `remove` 时产生 $O(n)$ 的移位操作，可将被删条目替换为数组的**最后一个条目**，再删除最后一个位置 → 找到索引后删除的时间复杂度为 $O(1)$。

---

## 3. 哈希表（§10.2）

**目标**：将 `get`、`put`、`remove` 的时间复杂度降至**期望 $O(1)$**。

### 核心思想

使用**哈希函数** $h$ 将键 $k$ 转换为**桶数组**（容量为 $N$）中的索引 $h(k) \in [0, N-1]$。

$$\text{键 } k \;\xrightarrow{\text{hashCode()}}\; \text{整数} \;\xrightarrow{\text{压缩}}\; \text{索引 } \in [0, N-1]$$

### 两个独立步骤（§10.2.1）

1. **哈希码**（*hash code*）：将键转换为整数 — **与 $N$ 无关**。
2. **压缩函数**：将整数映射到 $[0, N-1]$ — **依赖于 $N$**。

这种分离的优势在于：若调整表的大小，只有压缩函数需要改变；每个对象的 `hashCode()` 保持不变。

---

## 4. 哈希码（§10.2.1）

### 二进制表示

对于占用 $\leq$ 32 位的类型（`byte`、`short`、`int`、`char`），直接使用其整数值。对于 64 位类型（`long`、`double`），将高 32 位与低 32 位组合（通过求和或异或）。

### 多项式哈希码

对于字符串和变长对象 $(x_0, x_1, \ldots, x_{n-1})$，选择常数 $a \neq 0, 1$ 并计算：

$$x_0 \cdot a^{n-1} + x_1 \cdot a^{n-2} + \cdots + x_{n-2} \cdot a + x_{n-1}$$

通过**霍纳法则**高效计算：

$$x_{n-1} + a\bigl(x_{n-2} + a(x_{n-3} + \cdots + a(x_1 + a \cdot x_0) \cdots)\bigr)$$

$a \in \{33, 37, 39, 41\}$ 对于英文字符串特别有效（在 50,000 个单词中碰撞次数少于 7 次）。

### 循环移位哈希码

该变体将乘以 $a$ 替换为对二进制位进行**循环移位**。移位 **5 位**是最优选择（在 230,000 个英文单词中共产生 190 次碰撞，而移位 0 退化为简单求和则产生 234,735 次碰撞）。

```java
static int hashCode(String s) {
    int h = 0;
    for (int i = 0; i < s.length(); i++) {
        h = (h << 5) | (h >>> 27);   // 5-bit cyclic shift
        h += (int) s.charAt(i);
    }
    return h;
}
```

## 5. 压缩函数（§10.2.1）

### 除法方法

$$h(k) = i \bmod N$$

若 $N$ 为**素数**，分布效果更好。若 $N$ 不是素数，哈希码中的规律性模式会重复出现。

### MAD 方法（*Multiply-Add-and-Divide*，乘加除法）

$$h(k) = \bigl[(a \cdot i + b) \bmod p\bigr] \bmod N$$

其中 $p$ 为大于 $N$ 的素数，$a \in [1, p-1]$，$b \in [0, p-1]$，随机选取。

MAD 方法比简单除法更能消除规律性模式。

---

## 6. 碰撞处理（§10.2.2）

当两个不同的键 $k_1 \neq k_2$ 具有相同的哈希值 $h(k_1) = h(k_2)$ 时，发生**碰撞**。

### 分离链接法（*Separate Chaining*）

每个桶 $A[j]$ 包含一个**小型辅助映射**（通常为 `UnsortedTableMap`），存储所有哈希值等于 $j$ 的条目。

- 装载因子 $\lambda$ **可以超过 1**。
- 删除简单（无需哨兵）。
- 期望代价：每次操作 $O(1 + \lambda)$。

### 开放寻址法（*Open Addressing*）

条目**直接存储在数组中**。若桶 $A[h(k)]$ 已被占用，则探测后续桶。

| 策略                | 探测序列 $f(i)$                       | 主要问题           |
|---------------------|---------------------------------------|---------------------|
| 线性探测            | $f(i) = i$                            | 一次聚集            |
| 二次探测            | $f(i) = i^2$                          | 二次聚集            |
| 双重哈希            | $f(i) = i \cdot h'(k)$               | 计算开销较大        |

- $\lambda$ **必须保持 $< 1$**（条目数不能超过槽位数）。
- 删除操作需要使用 **DEFUNCT** 标记（哨兵），以免破坏探测链。

---

## 7. 装载因子与再哈希（§10.2.3）

**装载因子**为 $\lambda = n / N$（$n$ = 条目数，$N$ = 数组容量）。

### 推荐阈值

| 策略            | 最大 $\lambda$ 阈值                         |
|-----------------|----------------------------------------------|
| 分离链接法      | $< 0.9$（Java 默认使用 0.75）                |
| 开放寻址法      | $< 0.5$（线性探测）                          |

### 再哈希

当 $\lambda$ 超过阈值时：

1. 创建一个大小约为 $2N$ 的**新数组**（最好为素数）。
2. 对每个条目**重新计算压缩函数**（而非 `hashCode()`！）。
3. 将所有条目重新插入新数组。

再哈希的代价在均摊意义下为每次操作 $O(1)$（与动态数组扩容的分析相同）。

---

## 8. Java 中的 `hashCode()` / `equals()` 契约（§10.2.1）

**基本规则**：若 `x.equals(y)` 返回 `true`，则 `x.hashCode() == y.hashCode()` **必须**为真。

其逆命题是**假的**：两个不相等的对象*可以*具有相同的哈希码（这就是碰撞）。

若重写了 `equals()` 而未重写 `hashCode()`，"相等"的对象可能落入不同的桶中 → 映射将无法检索到这些条目。

---

## 9. 复杂度总结（教材表 10.2）

| 方法                           | `UnsortedTableMap` | 哈希表（期望）        | 哈希表（最坏情况）    |
|--------------------------------|--------------------|-----------------------|-----------------------|
| `get`                          | $O(n)$             | $O(1)$                | $O(n)$                |
| `put`                          | $O(n)$             | $O(1)$                | $O(n)$                |
| `remove`                       | $O(n)$             | $O(1)$                | $O(n)$                |
| `size`, `isEmpty`              | $O(1)$             | $O(1)$                | $O(1)$                |
| `entrySet`, `keySet`, `values` | $O(n)$             | $O(n)$                | $O(n)$                |

最坏情况 $O(n)$ 发生在所有键具有相同哈希码时。

# 第二部分 — 练习

## 1. 判断正误

??? question "Q1 — 键的唯一性"

    在映射中，两个不同的条目可以具有**相同的键**。

    ??? success "答案"

        **错误。** 键按定义是**唯一的**。若在已有条目 $(k, v1)$ 的情况下调用 `put(k, v2)`，则该值会被**替换**，旧值 $v1$ 被返回。映射的大小不变。

??? question "Q2 — UnsortedTableMap 的复杂度"

    在 `UnsortedTableMap` 中，`put(k, v)` 操作总是以 $O(1)$ 运行。

    ??? success "答案"

        **错误。** 在插入之前，`put` 必须先**查找**键 $k$ 是否已经存在（通过 `findIndex`），这需要线性扫描 → 最坏情况为 $O(n)$。若键是新的，插入本身是 $O(1)$，但前期查找占主导地位。

??? question "Q3 — 哈希码与压缩函数"

    对象的哈希码取决于哈希表的大小 $N$。

    ??? success "答案"

        **错误。** **哈希码**与 $N$ 无关 — 依赖于 $N$ 的是**压缩函数**。这正是将哈希分为两步的主要优势：若调整表的大小，压缩函数改变，但每个对象的哈希码不变。

??? question "Q4 — 分离链接法与装载因子"

    使用分离链接法时，装载因子 $\lambda$ 永远不会超过 1。

    ??? success "答案"

        **错误。** 使用分离链接法时，$\lambda$ **可以超过 1**，因为每个桶包含一个链表，可以存放任意数量的条目。**开放寻址法**才要求 $\lambda \leq 1$（每个槽只能存放一个条目）。

??? question "Q5 — DEFUNCT 哨兵"

    使用开放寻址法（线性探测）时，可以直接将槽置为 `null` 来删除一个条目。

    ??? success "答案"

        **错误。** 置为 `null` 会破坏探测链。如果键 $k_1$ 是在探测越过 $k_2$ 的位置后才被插入的，那么将 $k_2$ 置为 `null` 删除后，对 $k_1$ 的查找会失败（探测会在 `null` 处提前终止）。必须使用 **DEFUNCT** 标记来区分"已删除的槽"与"从未使用的槽"。

??? question "Q6 — 线性聚集"

    二次探测完全解决了开放寻址法中的聚集问题。

    ??? success "答案"

        **错误。** 二次探测消除了线性探测特有的**一次聚集**（连续块），但它引入了自身的问题，称为**二次聚集**：哈希到同一桶的键总是遵循相同的探测序列。**双重哈希**能更有效地避免两种形式的聚集。

??? question "Q7 — hashCode/equals 契约"

    若两个对象具有相同的 `hashCode()`，则 `equals()` 必然返回 `true`。

    ??? success "答案"

        **错误。** 契约仅规定 `equals() == true` **蕴含**相同的 `hashCode()`。逆命题为假：两个不相等的对象*可以*具有相同的哈希码 — 这正是**碰撞**的定义。只有 `equals → hashCode` 这个方向是有保证的。

## 2. 单项选择题

??? question "Q1 — 多项式哈希码"

    使用 $a = 33$ 计算字符串 `"ABC"` 的多项式哈希码，Unicode 值为 $A=65$、$B=66$、$C=67$。

    公式为：$x_0 \cdot a^2 + x_1 \cdot a + x_2$

    结果是什么？

    - [ ] A) 198
    - [ ] B) 73 030
    - [ ] C) 2 211
    - [ ] D) 65 033

    ??? success "答案"

        **B) 73 030**

        计算过程：

        - $65 \times 33^2 + 66 \times 33 + 67$
        - $= 65 \times 1089 + 66 \times 33 + 67$
        - $= 70\,785 + 2\,178 + 67$
        - $= 73\,030$

        用霍纳法则：$67 + 33 \times (66 + 33 \times 65) = 67 + 33 \times (66 + 2145) = 67 + 33 \times 2211 = 67 + 72\,963 = 73\,030$ ✓

??? question "Q2 — MAD 压缩"

    MAD 压缩参数为 $a = 3$、$b = 5$、$p = 11$、$N = 7$。

    哈希码为 $i = 15$ 的键对应的索引是什么？

    - [ ] A) 1
    - [ ] B) 3
    - [ ] C) 5
    - [ ] D) 6

    ??? success "答案"

        **D) 6**

        计算：$[(3 \times 15 + 5) \bmod 11] \bmod 7 = [50 \bmod 11] \bmod 7 = 6 \bmod 7 = 6$

??? question "Q3 — 分离链接法：负载最重的桶"

    大小为 $N = 13$ 的哈希表，压缩函数 $h(k) = k \bmod 13$。

    插入以下键：$\{18, 41, 22, 44, 59, 32, 31, 73\}$。

    哪个桶包含最多条目，有多少个？

    - [ ] A) 桶 9，有 2 个条目
    - [ ] B) 桶 5，有 3 个条目
    - [ ] C) 桶 6，有 3 个条目
    - [ ] D) 桶 2，有 2 个条目

    ??? success "答案"

        **B) 桶 5，有 3 个条目**

        分布情况：

        | 键  | $k \bmod 13$ | 桶  |
        |-----|-------------|-----|
        | 18  | 5           | 5   |
        | 41  | 2           | 2   |
        | 22  | 9           | 9   |
        | 44  | 5           | 5   |
        | 59  | 7           | 7   |
        | 32  | 6           | 6   |
        | 31  | 5           | 5   |
        | 73  | 8           | 8   |

        桶 5 包含 $\{18, 44, 31\}$ → **3 个条目**。

??? question "Q4 — 除法方法何时足够？"

    在哪种情况下，压缩函数 $h(k) = k \bmod N$ **通常足够**？

    - [ ] A) 键是连续整数（1001、1002、1003、……）
    - [ ] B) $N$ 是素数且哈希码已经分布均匀
    - [ ] C) $N$ 是 2 的幂次且键仅在高位比特上有差异
    - [ ] D) 哈希表几乎已满（$\lambda \approx 1$）

    ??? success "答案"

        **B)**

        当 $N$ 为素数且哈希码没有规律性模式时，除法方法效果良好。选择素数 $N$ 有助于"分散"分布。选项 A 在 $N$ 为素数时也能正常工作，但选项 B 更具一般性。选项 C 有问题，因为 2 的幂次只保留低位比特 — 高位比特的差异会丢失。选项 D 涉及装载因子管理，与压缩质量无关。

??? question "Q5 — 再哈希时重新计算什么？"

    当哈希表扩容时，每个条目需要重新计算什么？

    - [ ] A) 对象的 `hashCode()`
    - [ ] B) 压缩函数的结果（数组中的索引）
    - [ ] C) `equals()` 方法
    - [ ] D) 装载因子的定义

    ??? success "答案"

        **B)**

        对象的 `hashCode()` 是其固有属性 — 在再哈希过程中不会改变。然而，**压缩函数**依赖于数组大小 $N$（例如 $i \bmod N$）。由于 $N$ 发生变化，每个条目在新数组中的索引必须重新计算。这也正是哈希码与压缩函数分离的意义所在。

??? question "Q6 — 网络缓存：选择哪种策略？"

    在设计一个网络缓存（键 = URL，值 = 内容）时，**删除操作非常频繁**（页面定期过期）。哪种碰撞策略最合适？

    - [ ] A) 线性探测的开放寻址法
    - [ ] B) 双重哈希的开放寻址法
    - [ ] C) 分离链接法
    - [ ] D) 无需特殊策略 — `UnsortedTableMap` 即可满足需求

    ??? success "答案"

        **C) 分离链接法**

        **频繁删除**是关键判断标准。使用开放寻址法时，每次删除都需要一个 DEFUNCT 哨兵，随着 DEFUNCT 标记的积累，性能会逐渐下降（探测链变长）。使用分离链接法时，删除操作简单直接 — 只需从辅助链表中移除一个节点，对其他条目没有任何副作用。

## 3. 进阶问题

??? question "Q7 — 装载因子数值计算"

    一个哈希表使用**分离链接法**，有 $N = 100$ 个桶，包含 $n = 250$ 个条目。假设**均匀哈希**（每个桶被选中的概率相同）。

    调用 `get(k)` 时，期望检查的元素数量是多少？

    - [ ] A) 1
    - [ ] B) 2.5
    - [ ] C) 25
    - [ ] D) 250

    ??? success "答案"

        **B) 2.5**

        装载因子为 $\lambda = n/N = 250/100 = 2.5$。

        在均匀哈希下，每个桶的期望大小为 $\lambda = 2.5$。一次成功的 `get` 的代价与包含该键的桶的大小成正比 → 平均需要检查 **2.5 个元素**。

??? question "Q8 — $O(1)$ 何时消失"

    使用一个**固定**容量 $N$ 的哈希表（不进行再哈希），不断插入条目而从不扩容。

    当 $n \to \infty$ 时，`get(k)` 的期望复杂度变为多少？请给出理由。

    ??? success "答案"

        期望代价为 $O(1 + \lambda) = O(1 + n/N)$。

        若 $N$ 固定而 $n \to \infty$，则 $\lambda \to \infty$，代价变为 **$O(n)$** — 哈希的优势消失了。

        这正是**再哈希**不可或缺的原因：它将 $\lambda$ 保持在一个常数范围内，从而保证期望 $O(1)$。再哈希本身的代价均摊后为每次操作 $O(1)$。

??? question "Q9 — 构造一个"病态" `hashCode()`"

    给出一个合法的 Java `hashCode()` 实现，使其**满足** `equals`/`hashCode` **契约**，但会导致哈希表的**最坏情况**。解释其对性能的影响。

    ??? success "答案"

        ```java
        @Override
        public int hashCode() {
            return 1;  // constante — valide mais catastrophique
        }
        ```

        **为何合法**：契约要求 `equals == true` 蕴含相同的 `hashCode`。这里*所有*对象的哈希码都相同，因此该条件被平凡地满足（所有对象的哈希码相同，特别是相等对象的哈希码也相同）。

        **影响**：所有条目都落入**同一个桶**中。使用分离链接法时，该桶变成一个大小为 $n$ 的链表 → `get`、`put`、`remove` 操作退化为 **$O(n)$**（与 `UnsortedTableMap` 的行为相同）。

        这也是教材（§10.2.3）中描述的 DoS 攻击向量：攻击者可以预先计算出共享同一哈希码的字符串，以此使 Web 服务器过载。

??? question "Q10 — 内存权衡：链接法与开放寻址法"

    在以下两种场景中，比较**分离链接法**与**开放寻址法**的内存开销：

    1. 存储的对象**非常小**（约 8 字节）。
    2. 存储的对象**非常大**（约 2 KB）。

    ??? success "答案"

        **场景 1 — 小对象（约 8 字节）：**

        使用分离链接法时，每个条目都有**节点/引用开销**（辅助链表中每个条目通常占 16–32 字节）。对于 8 字节的有效载荷，内存开销可能会**翻倍甚至三倍**。

        使用开放寻址法时，条目直接存储在数组中 — 无需辅助节点。唯一的开销来自空槽（由于必须保持 $\lambda < 0.5$，数组中大约一半的槽是空的）。

        **→ 对于小对象，开放寻址法更加紧凑。**

        **场景 2 — 大对象（约 2 KB）：**

        链接法的每个节点开销（16–32 字节）与 2 KB 的有效载荷相比**可以忽略不计**（< 2%）。相比之下，开放寻址法浪费了约 50% 的数组空间用于空槽，且每个空槽占用一个完整条目的大小（或一个引用，取决于实现）。

        **→ 对于大对象，链接法的相对开销极小，且链接法还提供了更简单的删除操作。**

??? question "Q11 — 重写 `equals()` 而未重写 `hashCode()`"

    创建一个 `Student` 类，基于学号重写了 `equals()`，但**忘记**重写 `hashCode()`。在 Java `HashMap` 中使用 `Student` 实例作为键。

    可能会发生什么？为什么？

    ??? success "答案"

        **Java 契约被违反**：`equals()` 返回 `true`，但 `hashCode()` 返回不同的值（因为从 `Object` 继承的默认版本基于内存地址）。

        **具体后果：**

        1. 两个学号相同的 `Student` 对象会被 `equals()` 判定为"相等"，但可能落入 `HashMap` 的**不同桶**中。
        2. 执行 `map.put(student1, grade)` 后再执行 `map.get(student2)`（其中 `student1.equals(student2)` → `true`）可能返回 `null`，因为 `student2` 被查找的桶与 `student1` 被插入的桶不同。
        3. 同一个逻辑键可能产生**多个条目**，从而违反映射契约。

        **结论**：任何对 `equals()` 的重写都必须伴随对 `hashCode()` 的一致性重写。

??? question "Q12 — 完整轨迹（分离链接法）"

    使用容量为 $N = 7$ 的**分离链接法**哈希表。

    键为 2 个字符的字符串。对于键 $s = s_0 s_1$：

    - **哈希码**：$hc(s) = 1 \cdot code(s_0) + 2 \cdot code(s_1)$
    - **压缩函数**：$h(s) = hc(s) \bmod 7$

    在每个桶的**链表头部**插入新条目。

    执行以下轨迹，给出：

    1. 每次操作的返回值；
    2. 哈希表的最终状态（每个非空桶的内容）。

    轨迹：

    1. `put("AX", 10)`
    2. `put("HQ", 20)`
    3. `put("BY", 30)`
    4. `put("CZ", 40)`
    5. `put("DX", 50)`
    6. `get("HQ")`
    7. `remove("BY")`
    8. `put("EY", 60)`
    9. `get("BY")`

    ??? success "答案"

        **桶的计算**

        | 键   | $hc(s)$                     | $h(s)=hc \bmod 7$ |
        |------|-----------------------------|-------------------|
        | AX   | $65 + 2 \cdot 88 = 241$     | 3                 |
        | HQ   | $72 + 2 \cdot 81 = 234$     | 3                 |
        | BY   | $66 + 2 \cdot 89 = 244$     | 6                 |
        | CZ   | $67 + 2 \cdot 90 = 247$     | 2                 |
        | DX   | $68 + 2 \cdot 88 = 244$     | 6                 |
        | EY   | $69 + 2 \cdot 89 = 247$     | 2                 |

        **操作返回值**

        1. `put("AX", 10)` → `null`
        2. `put("HQ", 20)` → `null`
        3. `put("BY", 30)` → `null`
        4. `put("CZ", 40)` → `null`
        5. `put("DX", 50)` → `null`
        6. `get("HQ")` → `20`
        7. `remove("BY")` → `30`
        8. `put("EY", 60)` → `null`
        9. `get("BY")` → `null`

        **最终状态**

        - 桶 2：`("EY",60) -> ("CZ",40)`
        - 桶 3：`("HQ",20) -> ("AX",10)`
        - 桶 6：`("DX",50)`

??? question "Q13 — 完整轨迹（开放寻址法）"

    使用容量为 $N = 11$ 的**开放寻址法**（线性探测）哈希表。

    对于整数键 $k$：

    - **哈希码**：$hc(k) = 2k + 5$
    - **MAD 压缩**：$h(k) = \bigl[(3 \cdot hc(k) + 7) \bmod 31\bigr] \bmod 11$
    - **探测**：$p_t(k) = (h(k) + t) \bmod 11$

    使用 `DEFUNCT` 哨兵进行删除。

    执行以下轨迹，给出：

    1. 每次操作的返回值；
    2. 哈希表的最终状态（非空索引）。

    轨迹：

    1. `put(10, "A")`
    2. `put(41, "B")`
    3. `put(72, "C")`
    4. `put(21, "D")`
    5. `remove(41)`
    6. `get(72)`
    7. `put(103, "E")`
    8. `get(41)`
    9. `put(54, "F")`

    ??? success "答案"

        **初始索引计算**

        | $k$ | $hc(k)=2k+5$ | $h(k)=((3hc+7)\bmod 31)\bmod 11$ |
        |-----|--------------|-----------------------------------|
        | 10  | 25           | 9                                 |
        | 41  | 87           | 9                                 |
        | 72  | 149          | 9                                 |
        | 21  | 47           | 2                                 |
        | 103 | 211          | 9                                 |
        | 54  | 113          | 5                                 |

        键 10、41、72、103 都从索引 9 出发，因此执行线性探测。

        **操作返回值**

        1. `put(10, "A")` → `null`
        2. `put(41, "B")` → `null`
        3. `put(72, "C")` → `null`
        4. `put(21, "D")` → `null`
        5. `remove(41)` → `"B"`（该槽标记为 `DEFUNCT`）
        6. `get(72)` → `"C"`（查找过程穿越 `DEFUNCT` 槽）
        7. `put(103, "E")` → `null`（复用第一个 `DEFUNCT` 槽）
        8. `get(41)` → `null`
        9. `put(54, "F")` → `null`

        **最终状态（非空索引）**

        - 0：`(72,"C")`
        - 2：`(21,"D")`
        - 5：`(54,"F")`
        - 9：`(10,"A")`
        - 10：`(103,"E")`
